## Context

`zally-chain` exposed two retry-classification primitives:

1. A boolean field `is_retryable: bool` carried on the catchall variants `ChainSourceError::Unavailable`, `ChainSourceError::UpstreamFailed`, `SubmitterError::Unavailable`, `SubmitterError::UpstreamFailed`, plus mirror copies on `WalletError::ChainSource` and `WalletError::SyncDriverFailed`.
2. A 50-line mapping table `zinder_source::zinder_error_to_chain_source` that collapsed thirteen typed `IndexerError` variants into the two zally-side catchalls, hand-picking `is_retryable` per variant.

This design is the same shape that produced the zinder 2026-05-15 production incident (writer exits on an unknown JSON-RPC error code). The bool cannot describe operator-action failures distinctly from caller-bug failures, and the mapping table loses every typed identity the upstream client already provides. New `IndexerError` variants default to `UpstreamFailed { is_retryable: false }` until the table is updated, which means a future zinder release can silently degrade.

In parallel, `zinder-client` already exposes `IndexerError::retry_policy() -> RetryPolicy` with five variants (`RetryWithBackoff`, `RefreshChainEpoch`, `RestartFromEarliestRetained`, `OperatorActionRequired`, `ClientError`) that is documented to be stable across zinder releases. Zally was re-deriving this classification with strictly less information.

Two of those five describe an expired source boundary rather than a failure: the caller pinned a chain epoch or an event cursor, the source moved past it, and the caller has to re-acquire the boundary and restart its bounded operation. Zinder's wallet-serving pair retains exactly one epoch and rotates it on every canonical append, so on a network with 75-second blocks a sync attempt that outlives one block always ends this way. Collapsing that signal into `Retryable` makes a once-per-block control event count as backend trouble: the circuit breaker crosses its threshold, `WalletError::CircuitBroken` starts short-circuiting sync before any work happens, those empty attempts strike the repair ladder, and the driver parks a wallet whose only problem was being behind. The further behind the wallet is, the more rotations its catch-up spans, so the breaker trips fastest exactly when catch-up matters most.

## Decision

1. **`FailurePosture` replaces `is_retryable: bool`.** A new enum `zally_core::FailurePosture { Retryable, Restartable, RequiresOperator, NotRetryable }` is the single operator-facing classification used at the wallet boundary. Labels (`retryable`, `restartable`, `requires_operator`, `not_retryable`) match the posture vocabulary already used in zally documentation and align with zinder's `RetryPolicy`; `Restartable` covers both zinder policies that name a boundary restart (`RefreshChainEpoch`, `RestartFromEarliestRetained`), which zally consumes identically.

   `Restartable` means the source answered precisely and is serving: the pinned boundary expired, re-issuing the identical request can never succeed, and the caller re-acquires the boundary and restarts the bounded operation. It is not evidence of backend health, so it must never reach the circuit breaker. The unit that restarts is the caller's, not the source's: for sync that unit is one `Wallet::sync` attempt, which re-pins from `ChainSource::current_epoch` on entry (ADR-0005 decision 5).

2. **`ChainSourceError` and `SubmitterError` drop the catchall variants.** `Unavailable { reason }` is retained as the generic Retryable signal for source-agnostic consumers (the testkit mock, any future non-zinder `ChainSource`). `UpstreamFailed { reason, is_retryable }` is deleted. A new variant `Indexer(#[from] IndexerError)` carries the typed zinder error lossless when the `zinder` feature is enabled. Posture is derived via a `posture()` method that delegates to `IndexerError::retry_policy()` for the `Indexer` variant and statically classifies the other variants.

3. **`WalletError::ChainSource` becomes a tuple variant `ChainSource(#[from] ChainSourceError)`.** Same shape for `Submitter(#[from] SubmitterError)`. The `reason: String` and `is_retryable: bool` fields are removed; consumers read the inner error directly. `WalletError::SyncDriverFailed` keeps its `reason` field and drops `is_retryable: bool`; the variant is surfaced only by `SyncHandle::close` for a panicked driver task, so its posture is statically `RequiresOperator`.

4. **One typed-error path, no string adapters.** The standalone mapper functions `zinder_source::zinder_error_to_chain_source`, `zinder_submitter::zinder_error_to_submitter_error`, `sync::map_chain_source_error`, `wallet::map_chain_source_to_wallet_error`, `pczt::map_submitter_error`, and `spend::map_submitter_error` are deleted. The `#[from]` attributes on the new tuple variants let `?` carry zinder errors directly to the wallet boundary with the typed `IndexerError` preserved. The lossy `IndexerError::DataLoss` → `MalformedCompactBlock { block_height: BlockHeight::from(0), ... }` placeholder is gone.

5. **`IsRetryable` becomes `HasFailurePosture`.** The retry trait in `zally-wallet::retry` exposes `failure_posture() -> FailurePosture` instead of `is_retryable() -> bool`. The posture answers the two decisions separately: `FailurePosture::allows_retry` gates `with_retry` re-invoking the operation and holds for `Retryable` and `Restartable`; `FailurePosture::trips_circuit_breaker` gates `with_breaker_and_retry` counting the failure and holds for `Retryable` alone.

   Bypassing the breaker means recording nothing, not recording a success. The breaker has exactly one success rule: a call that completed. That rule is what a half-open probe asks about, because a half-open probe exists to find out whether a source that was failing can finish a unit of work again. An expired boundary, a missing capability, and an out-of-bounds request all end without doing that unit of work, so none of them may answer the probe or clear a failure streak. `with_breaker_and_retry` therefore leaves the breaker untouched for every failure it does not count, and a source that is genuinely broken keeps its cooldown even while it is precise enough to reject pins.

6. **The repair ladder treats an expired boundary as `SyncRepair::Retry`.** The sync driver's `repair_for` maps `Restartable` to the same rung as `Retryable`: no state repair, since nothing about the wallet's derived state is wrong. Combined with the existing rule that a `Retry`-classified fault which advanced the scanned height publishes `wallet_sync_slow_progress` instead of striking the ladder, a wallet that keeps committing chunks catches up indefinitely across rotations. An attempt that expires without committing anything still strikes the ladder, so a source rotating faster than the wallet can fetch one chunk keeps its escape hatch to `SyncRepair::Park` and the park reprobe.

   **Checked progress is what the driver reports as sync freshness.** `SyncSnapshot::last_observation` carries a `SyncObservation { scanned_to_height, observed_at_ms }`, written when the wallet has both committed chain state and compared it against the chain: a run that finished, and a `Retry`-classified fault whose iteration advanced the wallet's persisted scan frontier after the comparison passed. A consumer gating spends on wallet freshness needs age and distance together, so it pairs `observed_at_ms` with `lag_blocks`.

   The comparison is what makes the stamp safe, so it runs first. `scan_and_emit` calls `verify_tree_roots` immediately after `scan_blocks`, ahead of the event fan-out, which puts the wallet's only detector for a corrupt commitment tree on the near side of every read that can outlive the pin; it is also the last chain read a scan attempt makes; the transparent-UTXO refresh runs on its own cadence off the scan attempt entirely (ADR-0005 decision 7) and never contributes to this tail. A chunk whose comparison still outruns the pin surfaces as `WalletError::UnverifiedScanChunk`, classified on whatever stopped the comparison and carrying its blocks forward as progress, but earning no observation: the wallet holds state nothing has checked, and a divergence it never detected would otherwise read as fresh and route spends onto an anchor the network rejects. A run that scanned no blocks compared nothing, so it re-dates the observation only up to a height already checked, which stops a caught-up cycle from laundering an unchecked chunk into agreement.

   An attempt that committed nothing writes nothing, and neither does a fault on a state-repair rung: those blocks sit on a view the wallet has just been told to distrust. The driver measures an attempt's progress across two direct reads of the persisted frontier, and a read it could not make counts as no progress; substituting the last published height would credit an attempt that read nothing with every block the wallet had ever scanned.

7. **Boundary-error types keep their bool.** `StorageError`, `SealingError`, `KeyDerivationError`, and `PcztError` retain their `is_retryable()` method because their domains only need a binary retry signal. The wallet-side `HasFailurePosture` impl maps their bool to `{Retryable, NotRetryable}` mechanically.

8. **Testkit injects errors via a closure factory.** `MockChainSource::fail_current_epoch_next` and `MockSubmitter::fail_submit_next` take `impl FnMut() -> ChainSourceError` rather than a single cloneable error. This removes the `Clone` derive requirement on error types (which would otherwise force an `Arc<IndexerError>` indirection because zinder-client's `IndexerError` does not implement `Clone`).

## Consequences

- A new `IndexerError` variant lands in zally with its correct `RetryPolicy`-derived posture as soon as zinder ships it. There is no zally-side adapter to forget.
- Operator dashboards have access to the typed cause (`zinder indexer error: invalid request: …`) instead of the previous adapter-rewritten string (`zinder rejected the request: …`).
- The circuit breaker is no longer poisoned by operator-action failures. A misconfigured upstream (`IndexerError::FailedPrecondition`) or a malformed compact block (`ChainSourceError::MalformedCompactBlock`) leaves the breaker where it was; only genuine transient backend trouble flips it open.
- Epoch rotation and cursor expiry are free: a wallet thousands of blocks behind meets them on every attempt and still converges, because each attempt keeps the blocks it committed before the boundary moved and the next attempt re-pins.
- A half-open breaker can now stay half-open indefinitely, when every probe ends in a class the breaker does not judge. That is honest (nothing has been learned) and it is not a hole: `CircuitBreakerState::HalfOpen` is visible in `WalletStatus`, and hammering an unproductive source is the repair ladder's job, which parks it.
- A catch-up under a rotating source keeps its chunks and its root comparisons: the comparison sits at the head of the post-commit tail, where an epoch that lasts one block still covers it. When a chunk does outrun it, `WalletError::UnverifiedScanChunk` names the height and the cause, the driver publishes the slow-progress transition carrying it, and wallet freshness stops advancing until a later chunk is checked.
- A wallet caught up at the tip keeps re-dating its freshness on each caught-up cycle, because the height that cycle reports is one an earlier chunk already checked. A freshly started driver has checked nothing yet, so a wallet that starts already caught up publishes no freshness until the next block gives it a chunk to check. A consumer gating spends on freshness stays closed across that window.
- `FailurePosture` gains a variant. It is `#[non_exhaustive]`, so consumers already carry a wildcard arm, but any consumer whose wildcard assumed three classes should classify `Restartable` explicitly: a wildcard that falls through to a state repair would rewind the wallet once per block.
- `WalletError::ChainSource` and `WalletError::Submitter` change from struct variants to tuple variants. Consumers that pattern-match must rewrite `Upstream::ChainSource { .. }` to `Upstream::ChainSource(_)`. There is no compatibility shim: the previous shape was the source of the bug class this ADR removes.
- The testkit failure-injection API takes a closure. Call sites change from `fail_current_epoch_next(2, ChainSourceError::Unavailable { reason: "…".into() })` to `fail_current_epoch_next(2, || ChainSourceError::Unavailable { reason: "…".into() })`. New tests can inject distinct errors per attempt without API friction.
- The sync driver lifecycle has no failed state: `SyncSnapshot::last_fault` (`SyncFault`) carries the repair classification (`SyncRepair`) the driver applies, and faults engage the repair ladder instead of terminating the task.
- `IsRetryable` is removed from the public surface; consumers that took `IsRetryable` as a trait bound import `HasFailurePosture` and call `failure_posture()`.

## Alternatives considered

- **Keep the catchall variants and translate posture in place.** Rejected: this preserves the bool as the load-bearing contract field and keeps zally's surface drifting from zinder-client's typed error. The mapping table would still need to be edited on every new `IndexerError` variant.
- **Re-export `zinder_client::RetryPolicy` directly as `zally_chain::RetryPolicy`.** Rejected: zally already names a struct `RetryPolicy` in `zally_wallet::retry` for retry-attempt configuration. Re-exporting the zinder name would collide on the word "policy" and confuse consumers about what kind of policy they are looking at.
- **Mirror zinder's seven-class `SourceFailureClass` taxonomy.** Rejected: `SourceFailureClass` lives in `zinder-source` (a server-side crate) and is designed for ingest-loop backoff cadence selection. The wallet boundary needs only the four classes it has a policy for; the seven labels would add labels the wallet cannot act on.
- **Absorb epoch rotation inside `ZinderChainSource` so the sync driver never sees it.** Rejected on reorg safety. The pinned epoch is what makes every artifact in one sync attempt belong to one chain: the anchor tree state at `scan_start - 1` and the compact blocks above it are handed to `scan_blocks` together, which appends those blocks' note commitments onto that anchor's frontier. Zinder retains exactly one epoch, and consecutive epochs are related by `ChainEvent::ChainReorged` as readily as by `ChainCommitted`, so a fresh epoch carries no promise of extending the expired one. A source that re-pinned mid-operation would splice artifacts from two chain views into one commitment tree; nothing at scan time would detect it, and the corruption would surface much later as a rejected shielded proof at spend time. The invariant is scoped to the caller's unit of work, which the source cannot see, so only the caller can restart it. ADR-0005 decision 5 already forbids mixing artifacts from two epochs.
- **Give epoch rotation a posture the circuit breaker skips, but leave `Retryable` covering cursor expiry.** Rejected: the two conditions have the same character. Both say the caller's pinned boundary moved, both make re-issuing the identical request permanently futile, and zinder classifies them as siblings. Splitting them would leave `ChainEventCursorExpired` as the one restart signal that still reads as backend trouble, and `RetryPolicy::RestartFromEarliestRetained` would keep falling through the adapter's conservative wildcard to `RequiresOperator`.
- **Record a success on the breaker for every failure it does not count.** Rejected: it is the same conflation this ADR removes, pointed the other way. While the breaker is closed it looks harmless (the counter is already at zero on a healthy source), but it makes a broken source able to re-close its own half-open probe: a source whose every call fails will still answer `ChainEpochPinUnavailable` precisely, so it would escape the breaker once per cooldown forever and the breaker would protect nothing. Nothing about the outcome of a call that never completed is evidence of recovery.
- **Wrap `IndexerError` in `Arc` to keep `Clone` on `ChainSourceError`.** Rejected after weighing the API ergonomics: `WalletError` does not derive `Clone` either, so cloning was never the cross-cutting invariant the testkit alone implied. Changing the mock factory to a closure is a smaller, more honest API change than adding an `Arc` indirection on every chain error.

## Revision History

- 2026-07-27: Added the `Restartable` posture for expired source boundaries (`ChainEpochPinUnavailable`, `ChainEventCursorExpired`), split the breaker decision out of `allows_retry` into `trips_circuit_breaker`, made every failure the breaker does not count neutral on it rather than a success, and pinned the repair-ladder rung for the class.
- 2026-07-27: Replaced `SyncSnapshot::last_outcome` with `SyncSnapshot::last_observation`, moved the tree-root comparison to the head of the post-commit tail, and bound the sync-freshness stamp to chunks that comparison checked (decision 6).
- 2026-08-03: Removed decision 6's transparent-UTXO-refresh framing from the freshness contract: the walk no longer runs inside a scan attempt (ADR-0005 decision 7), so the tree-root comparison is now the last chain read a scan attempt makes, and a scan attempt's freshness no longer depends on the wallet's transparent-receiver count.
