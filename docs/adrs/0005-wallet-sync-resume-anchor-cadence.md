## Context

`zcash_client_backend` ships a documented sync protocol (`data_api::chain` module docs): push commitment-tree subtree roots, call `update_chain_tip`, ask the wallet for work with `suggest_scan_ranges`, scan the `Verify` range first, then the rest, fetching the chain state for `range.start - 1` before each `scan_cached_blocks`. The protocol exists so the `from_height == from_state.block_height() + 1` precondition of `scan_cached_blocks` holds by construction, and so notes become witness-anchored (spendable) from subtree roots without scanning every historical block.

The first two revisions of this ADR hand-rolled the loop instead. The wallet computed `scanned_from = fully_scanned_height + 1` itself and fetched `from_state` from zinder's sparse tree-state checkpoints (one per ~100 blocks). It never primed subtree roots. Two failures followed:

- **Spendable balance zeroed.** With no subtree roots, the sqlite backend refuses to report a note spendable while the shard containing the ZIP-315 anchor has unscanned ranges at or below the anchor. The 2026-05-27 revision worked around this by scanning all the way to the live tip so the anchor always landed in fully-scanned territory; that forced a full linear birthday-to-tip scan.
- **The scan panicked and wedged.** `from_state` came from a checkpoint at-or-before `scanned_from - 1`, almost never exactly `scanned_from - 1`, so `scan_cached_blocks` hit its `assert_eq!` and panicked. The panic killed the single-threaded wallet-db actor, freezing the faucet ~11k blocks behind the tip.

Both are downstream of one decision: hand-rolling the loop instead of using the library protocol. zinder now serves a coherent tree state at any exact height (zinder ADR-0005, tree-state-at-height carve-out), which removes the last reason the loop had to be hand-rolled.

## Decisions

1. **Sync is driven by the library's scan-range orchestration, and the chain tip is recorded once per drain.** Each scan step primes subtree roots for every pool via `WalletStorage::put_subtree_roots`, asks `WalletStorage::suggest_scan_ranges` for the highest-priority range, and scans one chunk of it (bounded by `MAX_BLOCKS_PER_SYNC`) with `from_state` fetched at exactly `range.start - 1`. `Wallet::sync` calls `update_chain_tip(visible_tip)` and then runs one such step; `Wallet::scan_queued_range` runs one step against work the queue already holds. One `SyncDriver` wakeup is one drain: the first iteration calls `Wallet::sync`, every later iteration calls `Wallet::scan_queued_range`, and the wakeup ends when a step that recorded the tip reports no blocks.

   Recording the tip is what plans work, and it plans differently either side of `tip - PRUNING_DEPTH`. A scanned frontier at or below that height earns a `VERIFY_LOOKAHEAD`-wide `Verify` range, which outranks every bulk range `suggest_scan_ranges` can return. Re-recording between chunks re-queues that lookahead, so a wallet whose backlog is deeper than `PRUNING_DEPTH` would advance ten blocks per chunk for the whole backlog and never reach the bulk range at all. Recording once per drain leaves the bulk `ChainTip` range at the head of the queue for every chunk after the first, and a wallet already at the tip still learns about new blocks because each wakeup opens with a fresh record. The hand-rolled `scanned_from` arithmetic, the birthday fallback, and the linear single-range fetch are deleted.

   A drained queue is drained against the tip that opened the drain, not against the chain. A backlog takes long enough that the chain moves under it, so a `Wallet::scan_queued_range` reporting no blocks is a statement about the queue and not about the chain, and the driver answers it by recording the tip once more. That closing record either queues the blocks mined during the drain or confirms the wallet reached the chain, so a wakeup only goes quiet against a tip it just read.

2. **Subtree-root priming is mandatory and runs before planning.** `ChainSource::subtree_roots` carries each root's `completing_block_height`; the wallet records it through `put_subtree_roots` for every shielded pool so a note is witness-anchored from its subtree root without scanning the whole subtree. This is part of the spendable-zero fix: completed shards do not require a full linear scan, and `suggest_scan_ranges` can plan subtree-aligned work.

3. **Each sync attempt scans through one pinned epoch's visible tip.** `ChainSource::current_epoch()` returns visible and settled identities atomically. Every attempt pins its own epoch and passes it to every compact-block, tree-state, and subtree-root read, clamping its scan range to that epoch's visible height. `update_chain_tip` records the visible tip of the epoch that opened the drain, so later chunks scan a queue planned against a tip at or below the one they are clamped to; a reorg that lowers the tip mid-drain trims the clamp and surfaces as a continuity error rather than as an out-of-range fetch. This keeps the upstream wallet tip and scan queue aligned. Leaving the visible-to-settled gap unscanned can make an otherwise mature note unspendable when both the note and that gap occupy the same incomplete commitment-tree shard. Zinder's epoch pin makes every artifact in the settlement window immutable for the attempt; a later reorg is handled by Verify-range scanning and the repair ladder. The settled tip remains finality metadata for settlement-sensitive policy. Because zinder serves an exact tree state at `range.start - 1`, `from_height == from_state.block_height() + 1` holds for every `scan_cached_blocks` call and the upstream assert can no longer fire. Transparent-UTXO reads are not part of this attempt; see decision 7.

4. **Reorg recovery rewinds to the announced fork point; the relative ladder handles only what no event announced.** Zinder's `ChainReorged` event names the reverted range, so its fork point is `reverted.start_height - 1`. The `SyncDriver` applies the event before its next scan: it reads the source's tree state at the fork point under a fresh epoch and calls `WalletStorage::revert_blocks_above`, which wraps `truncate_to_chain_state` and lands the wallet at exactly that height. The truncation works at any depth. When the target lies below the oldest retained checkpoint, `zcash_client_sqlite` 0.23 truncates to that checkpoint, inserts the supplied frontier as a new checkpoint at the target, and truncates to it (`zcash_client_sqlite/src/wallet.rs:4709`); upstream tests cover a target `PRUNING_DEPTH + 10` blocks deep (`zcash_client_backend/src/data_api/testing/pool.rs:5318`). Earlier revisions said a rewind deeper than 100 blocks fails; that was the `truncate_to_height` contract, not this one.

   The driver rewinds only when the wallet holds a block above the fork point that the source no longer serves: the highest block the wallet scanned, capped at the source's visible tip, must carry the hash the source reports at that height. A replayed event the wallet already followed is therefore a no-op. Reorg events that arrive while the driver is draining a backlog are read between chunks, so an announced reorg replaces the ladder's relative rewind even when a scan meets the replacement chain first.

   `WalletStorage::scan_blocks` still surfaces `StorageError::ChainReorgDetected { at_height }` (`Retryable`) on a continuity error, and `WalletError::TreeRootsDiverged` still proves a corrupt tree. A divergence no event announced reaches the repair ladder, which rewinds relative to the scanned height through `REWIND_LADDER_BLOCKS` (10, then 100, then 1,000 blocks) before it rebuilds. The deepest rung matches the deepest reorg Zebra can present: Zebra commits a block to finalized state only once its best chain exceeds `MAX_BLOCK_REORG_HEIGHT` (1,000) blocks. No rewind lands below the block before the account birthday. Truncation deletes every queued range above the rewound frontier, so every rewind returns the drain to its first iteration: the next attempt is a `Wallet::sync` that re-records the tip and re-queues the work above the frontier. The `Verify`-priority range that record returns first re-validates the tip-adjacent blocks on every wakeup. The hand-rolled tip-regress detector and the `truncate_to_height`-based rewind (which snapped down to the nearest checkpoint and spiralled the scan backwards) stay deleted. A divergence the 1,000-block rung cannot clear escalates to a rebuild from the birthday through `Wallet::reset_to_birthday`; no operator reset is required.

5. **An expired epoch restarts the whole sync attempt.** Zinder reports `ChainEpochPinUnavailable` when it can no longer serve the requested immutable view. The client classifies this as `RefreshChainEpoch`, which zally carries as the `Restartable` posture ([ADR-0002](0002-source-failure-posture.md)); Zally discards the partial attempt, acquires a new epoch, and restarts every artifact read under that epoch. It never retries an artifact with the stale pin or mixes artifacts from two epochs. Restarting is the only safe response: consecutive epochs can be related by a reorg, so artifacts drawn from two of them may describe two different chains. Blocks already committed by `scan_blocks` survive the restart, so a wallet far behind still advances on every attempt. A rotated pin is expected and self-healing rather than evidence of a broken source; the repair ladder holds it at the `Retry` rung, which never escalates ([ADR-0002](0002-source-failure-posture.md) decision 6).

6. **The wallet-db actor `catch_unwind` is defense-in-depth, not the scan-continuity safety net.** With the canonical loop the continuity assert can no longer fire from the scan path, so the actor's panic isolation is a generic last-resort backstop; the supervisor watchdog remains the recovery boundary.

7. **Transparent-UTXO refresh runs on its own cadence, off the scan attempt.** `Wallet::refresh_transparent_utxos` pins one epoch and walks every wallet-owned transparent receiver, recording each receiver's UTXOs as soon as they are fetched rather than batching the whole walk into one final write; a rotation mid-walk aborts the attempt under decision 5's restart discipline rather than mixing two epochs' results, and the next attempt is safe to re-visit every receiver because `WalletStorage::record_transparent_utxos` is idempotent. `SyncDriver::sync_continuously` spawns this as a second loop alongside the block-scan loop, sharing the wallet and chain source but never an attempt, on `SyncDriverOptions::transparent_utxo_refresh_interval_ms`'s cadence; it waits one interval before its first attempt so the two loops' cold starts do not race the same source. The receiver walk previously ran inline in `Wallet::sync`, once in the caught-up path and once at the end of every scanned chunk. Its cost is unbounded in both the number of wallet-owned receivers and the chain source's per-receiver latency, so inlining it made every scan attempt's wall-clock cost, and therefore the `SyncSnapshot`/freshness heartbeat, scale with both. Decoupling it removes that scaling: a slow or growing receiver set costs wall-clock time in the refresh loop alone.

8. **The driver persists the chain-event cursor it has applied and resumes after it.** The cursor lives in the wallet database (`ext_zally_chain_event_cursor`). A reorg's cursor is recorded in the same database transaction as its rewind (`WalletDb::transactionally_with_extension`), so a crash keeps either the prior wallet and cursor or both effects of the rewind. Any other event's cursor is recorded as soon as the driver receives it, except one that follows a reorg the driver has not applied yet, which waits with that reorg. A restarted driver subscribes with `ChainEventStreamStart::AfterCursor`, so Zinder replays a reorg that happened while the wallet was stopped (Zinder ADR-0025). A wallet with no cursor subscribes from `EarliestRetained`.

   The source can refuse a recorded cursor in two ways, and both have one recovery. `ChainEventCursorExpired` means the cursor fell out of the source's retained window; `ChainEventCursorInvalid` means the source never issued it, for example after the Zinder store was rebuilt. The driver forgets the cursor and replays the retained window from `EarliestRetained`. Each replayed reorg passes the same hash check as a live one, so the replay rewinds only what left the chain. A reorg that fell out of retention before the wallet applied it surfaces as a continuity error on the next scan and reaches the ladder.

9. **Every rewind reconciles the payment ledger.** `revert_blocks_above` returns the receives and transactions it un-mined, and the wallet publishes `WalletEvent::ReorgDetected`, then `TransactionReverted` and `ShieldedReceiveReverted` for each, so a host that credited a deposit can hold or reverse it. The same database transaction copies every wallet-sent transaction mined above the target, with its raw bytes and expiry, into `ext_zally_reverted_broadcasts`. Once the driver is caught up it settles that ledger: a transaction the wallet has scanned mined again is retired (the scan already published `TransactionConfirmed`), and any other is submitted once more through the submitter given to `SyncDriver::with_submitter` while the next block can include it.

   A reverted transaction is a pending broadcast again, and nothing but the pending-broadcast verdict decides that it is dead. The truncation un-mines it, so `list_pending_broadcast_transactions` returns it with the other pending broadcasts, from the reverted-broadcast ledger when a rebuild discarded the transaction row. `retire_pending_broadcasts` judges it with `TransactionHeader::check_mineable` at the lower of the fully scanned height and the settled tip, where no unscanned block and no reorg within the source's bound can mine it. The wallet's own scan is the primary evidence that a broadcast mined; the chain source is a second guard, because the scan can miss a transaction it sent (decision 10) and a source can report history it lacks as absent. Before it frees anything, the verdict pins a source epoch whose visible tip covers the judged height and asks `ChainSource::transaction_status` at that epoch. It judges a transaction only when the source reports it not found there and the epoch is still the source's current one afterwards. One the source reports mined is recorded mined at that height with `record_confirmed_broadcast`, after the earlier steps of its send, and keeps its key. One it still holds, a failed lookup, a lookup that does not answer within `WalletOptions::source_lookup_timeout_ms`, or an epoch that does not cover the judged height waits for a later sync, and `WalletEvent::PendingBroadcastVerdictWithheld` reports the wait once. The `ChainSource::transaction_status` contract binds `NotFound` to mean absent from every canonical block the epoch makes visible; a source that cannot promise that must return an error instead. Zinder's client at the pinned revision answers every gRPC `NOT_FOUND` on an epoch-pinned lookup with `NotFound`, including the server's reports of unavailable history or a missing epoch, so a Zinder `NotFound` alone is not proof of absence, and the scan stays primary. A transaction that verdict rejects goes through `record_unmineable_transaction`, which drops its pending-broadcast and reverted-broadcast rows, frees its idempotency keys, and reopens the dispense holds finalized with it (ADR-0003 decision 9), all in one storage transaction. `WalletEvent::PendingBroadcastUnmineable` then reports it exactly once. Until then a retry with its key returns the original transaction, so a payment that can still be mined is never paid twice. The resubmission uses the same predicate at the visible tip. Rewinds leave holds and idempotency records untouched.

10. **A rebuild from the birthday keeps the payment ledger.** `WalletStorage::recreate_with_account` builds a fresh database beside the live file (`wallet.db.rebuild`), creates the account in it, copies every ledger table except the derived chain tips into it, and renames it over the live file. Derived chain state starts fresh; idempotency records, holds, finalized PCZTs, pending PCZT and broadcast inputs, reverted broadcasts, and the cursor survive. The live file is untouched until the rename, so a failure or crash leaves the prior wallet and ledger in place, and a stale sibling is discarded by the next rebuild. Rows are copied by the column names both databases share, so a ledger that predates an added column still carries across. Sidecar journals go with the file they belong to, so a stale journal is never replayed into the replacement.

    The rebuild discards the transaction records `zcash_client_sqlite` keeps, so it first carries every transaction the ledger still names, through an active idempotency key, the steps of the send that key pays, pending-broadcast rows, or an active hold finalized with it, into `ext_zally_reverted_broadcasts` with its raw bytes and expiry. The verdict keeps judging it after the rescan, and the driver can resubmit it. A transaction the ledger does not name is not carried: the send path never handed it to a submitter, or released its key because it can never be mined, and resubmitting it could pay the recipient again after its key built a replacement.

    The binding records every step of a send under its key (`ext_zally_send_steps`), and the rebuild carries all of them. The paying step of a ZIP 320 send spends an output of its funding step, and `zcash_client_backend` 0.25 matches a block's transparent inputs only against outputs it knew before that block. When a rescan meets both steps in one block, it would read the mined payment as never mined. Before each scan step, the wallet therefore stores the carried steps of every unsettled send in `zcash_client_sqlite` with `store_carried_send_steps` (`decrypt_and_store_transaction`, in submission order), so the funding step's output is known before the block that spends it. Storing a step records its output only when the rebuilt account knows the funding step's ephemeral (ZIP 320) address, and a fresh account knows only its first gap's worth of them. The rebuild therefore reads the highest ephemeral address index the prior wallet reserved or saw used, opens the rebuilt database with an ephemeral gap that reaches past it, so account creation derives every address up to it, and reserves those addresses (`reserve_next_n_ephemeral_addresses`), so no later send reuses one. Every step is stored again before each scan step until the paying step is mined, including a step the scan has already seen mined.

    The wallet's own scan is the primary evidence that a payment mined, so a send it may have scanned past blind is never judged unmineable. When a scan step cannot record an earlier step's output as the wallet's, or cannot store or check a send's steps for a reason a retry would repeat (bytes that do not parse, a statement the database rejects), `store_carried_send_steps` marks the send in `ext_zally_scan_blind_sends`, and the mark stays until the send is released: the scan that followed may already have passed the paying step, and an output recorded later does not make that scan see it. The verdict then never records the send unmineable, `WalletEvent::PendingBroadcastVerdictWithheld` reports the wait, and the source can still record it mined. A transient database failure (busy, locked, out of space or memory, or I/O) marks nothing: it fails the scan attempt, so no scan runs without the send's outputs and no verdict judges the send in that pass, and the next attempt stores it again. Any other failure to store the carried steps also fails the scan attempt instead of scanning blind. The mark is not carried across a rebuild, whose rescan judges coverage afresh. The carry selects a step by the ledger rather than by `zcash_client_sqlite`'s `created` flag, which a stored step lacks, so a second rebuild keeps the steps a first rebuild stored. The upstream fix, matching spends against outputs received earlier in the same block, is tracked as a librustzcash issue draft.

11. **A source that stops following the chain halts spends.** A source that cannot follow a reorg keeps serving its last chain, so a wallet that scans it looks healthy while it serves a frozen branch. Until Zinder reports a typed halt status, the driver watches freshness: once the source's visible tip has not moved for `SyncDriverOptions::visible_tip_stall_limit_ms` (30 minutes by default) and a fresh epoch read still shows it, the driver enters `SyncDriverPhase::SourceHalted` with `SourceHalt::VisibleTipStalled`. While halted it scans nothing, and `send_payment`, `shield_transparent_funds`, `propose_pczt`, and `extract_and_submit_pczt` return `WalletError::ChainSourceHalted`. The driver resumes as soon as a chain event or an epoch read shows the tip moved, and closing the driver lifts the refusal. `WalletEvent::SourceHalted` and `WalletEvent::SourceRecovered` report entering and leaving the halt, so a host can pause payouts without polling the driver's phase. Regtest chains that mine on demand stall by design, so hosts disable the check there. A typed halt status from the source maps onto another `SourceHalt` variant and enters the same halt through `SourceTipWatch::halt`, so the halt and resume path does not change.

12. **Spends require a source reorg window at least as deep as the node's reorgs.** Decision 9's promise that a payment is never paid twice rests on the settled tip: the verdict frees a key only for a transaction no block above the judged height can include, and the judged height is at or below the source's settled tip. That holds only while the source never replaces a settled block, so its reorg window must cover every reorg the node can produce. Zebra produces reorgs up to 1,000 blocks deep, while Zinder's default window was 100 blocks when this decision was made. Against a 100-block window, a 600-block reorg Zebra legitimately follows could mine a transaction whose key the wallet already freed and whose replacement it already paid.

    `ChainSource::reorg_window_blocks` reports the source's configured window; `ZinderChainSource` reads Zinder's `ServerInfo::reorg_window_blocks`. The minimum is wallet policy, `WalletOptions::minimum_source_reorg_window_blocks` (1,000 by default), so it binds with or without a `SyncDriver`. `Wallet::sync` and `Wallet::scan_queued_range` read the window right before a verdict would record a broadcast unmineable, and record nothing unless that read meets the minimum, so no key is freed and no hold reopened while the settled tip could still be replaced. A failed read, or one that does not answer within `WalletOptions::source_lookup_timeout_ms`, holds the verdict too. After a read showed the window too shallow, every call reads it again, with or without a broadcast to judge, so the spend refusal lifts without a driver once the source meets the minimum. Holding the verdict, not only new spends, matters: a key freed under a shallow window would stay free after the window was raised, and its retry would pay a replacement the deeper reorg could still double. The `SyncDriver` also reads the window when it starts, each time it reopens the chain-event stream, where a source restarted with a new configuration first shows, and on every polling wakeup until a read succeeds. New spends fail with `WalletError::SourceReorgWindowUnverified` (`Retryable`) while a driver has not read the window, and with `WalletError::SourceReorgWindowTooShallow` (`RequiresOperator`) while the last read showed a smaller one. `WalletEvent::SourceReorgWindowTooShallow` reports a shortfall, and `WalletEvent::SourceReorgWindowSufficient` a later read that meets the minimum. Scanning and receiving continue, and closing the driver lifts its spend refusal. An operator who accepts the weaker guarantee lowers or disables the option.

## Consequences

- The `spendable_zat: 0` wedge is closed at its root: completed subtree roots witness-anchor historical notes, while scanning through the pinned visible tip removes unscanned gaps from an incomplete tip shard. `get_wallet_summary(ConfirmationsPolicy::default()).spendable_value()` reports the real balance once the note has enough confirmations.
- The `scan_cached_blocks` panic is closed at its root: every `from_state` is fetched at the exact `range.start - 1` the wallet asked for, so the invariant holds by construction.
- Catch-up is faster: the wallet scans the tip-adjacent `Verify`/`ChainTip` ranges first and witnesses history from subtree roots, so spendability arrives before the full history is linearly scanned. A backlog costs one chunk per `MAX_BLOCKS_PER_SYNC` blocks rather than one per `VERIFY_LOOKAHEAD` blocks, and the per-chunk fixed cost (the tree-root comparison) is paid a hundredth as often.
- A scan attempt's wall-clock cost no longer depends on the wallet's transparent-receiver count or the chain source's per-receiver read latency: decision 7 moved that cost to its own loop, so `Wallet::sync`'s timeout and the block-scan repair ladder are sized for block-fetch and tree-comparison cost alone.
- The `BadExpiryHeight` class stays closed: `update_chain_tip` is the live head, so the proposal builder's target is `head + 1` and expiry sits above the head. Because only a recording step can end a wakeup, the head the spend path reads is the one the wallet observed at the end of the drain rather than at its start, and a spend admitted the moment the wallet reports caught up carries an expiry the chain has not passed.
- Reorgs of any depth Zebra can produce (up to 1,000 blocks) are recovered without an operator: announced ones at their exact fork point, unannounced ones through the ladder. Hosts see `WalletEvent::ReorgDetected` and the reverted activity. Recovery keeps idempotency records and holds, so a reverted withdrawal is resubmitted or expires but is never paid twice.
- A birthday rescan is a last resort that no longer costs the payment ledger. It does still discard the transaction records `zcash_client_sqlite` keeps, including raw transactions the wallet created and has not seen mined; the reverted-broadcast ledger keeps its own copies.
- Hosts that gate spends on sync freshness also get a source-health gate: a halted source makes the wallet refuse new spends instead of building them on a frozen branch.
- A deployment must run its chain source with a reorg window of at least 1,000 blocks, or spends are refused. For Zinder that means `reorg_window_blocks = 1000` (or more) for ingest, projector, and query; the settled tip then trails the visible tip by that many blocks, so SYNC-10 verdicts arrive that much later.

## Operator runbook

Reorg recovery is automatic. `StorageError::ChainReorgDetected` is `Retryable`, and a reorg the chain source announces never reaches the ladder at all; neither should surface except in metrics and in `wallet_sync_fork_point_rewound` and `wallet_rewound` events. A divergence no event announced walks the repair ladder: `Rewind` at 10, 100, and then 1,000 blocks, then `RescanFromBirthday`, which rebuilds derived state in-process from the sealed seed and keeps the payment ledger. Production cured a 114-block Testnet reorg on 2026-07-20 through compounding rewinds, with 76 seconds of degradation and no operator action.

An operator acts only when the driver parks (`SyncDriverPhase::Parked`) or halts (`SyncDriverPhase::SourceHalted`), or when spends are refused over the source's reorg window:

1. **Parked on a `RequiresOperator` fault** (missing sealed seed, network mismatch, an unsupported source response). Fix the cause named in `SyncSnapshot::last_fault`; the driver re-arms the ladder at `reprobe_at_ms`, or restart it.
2. **Halted on the source.** Check that the chain source still follows its node: its visible and settled tips should advance. A Zinder that parked on a reorg deeper than its window needs its own recovery (see Zinder's runbooks). Zally resumes by itself once the visible tip moves.
3. **Spends refused with `SourceReorgWindowTooShallow`.** Raise the chain source's reorg window to at least the driver's minimum (Zinder: `reorg_window_blocks`, which is part of its store identity; see Zinder's runbooks for raising it on an existing store) and restart it. The driver reads the new window when it reopens the chain-event stream and spends resume.
4. **Manual rebuild, only as a last resort** when the ladder parks after exhausting `RescanFromBirthday`. Stop the host, keep the sealed key material (`wallet.age`, `wallet.age.age-identity`), and call `Wallet::reset_to_birthday`, which keeps the ledger. Deleting `wallet.db` by hand also deletes the payment ledger: idempotency records, holds, and reverted broadcasts are lost, and a retried payout can then pay twice.

The circuit breaker is not involved: `NotRetryable` postures are excluded from breaker counting.

## Alternatives considered

- **Keep hand-rolling the loop and only fix `from_state` alignment.** Rejected: it would not fix the spendable-zero wedge (no subtree roots) and would keep re-deriving work the wallet's own scan queue already plans. The library protocol is the pattern other wallets copy; diverging from it is the entropy this revision removes.
- **Scan only through the settled tip.** Rejected: `update_chain_tip(visible_tip)` then leaves the visible-to-settled gap in the upstream scan queue. If that gap shares an incomplete commitment-tree shard with a mature note, the shard remains above `ScanPriority::Scanned` and the upstream balance query reports the note as unspendable. A pinned `ChainEpoch` already prevents artifacts from changing within one attempt; later canonical replacement is handled by Verify-range scanning and reorg recovery.
- **Adopt the full async `sync` feature / `BlockCache` machinery.** Deferred: the in-process single-chunk fetch plus `suggest_scan_ranges` is sufficient and smaller. The minimum correct design is subtree priming + suggest-driven ranges + exact-boundary `from_state` + `Verify`-first ordering + `truncate_to_chain_state`.
- **Keep the payment ledger in its own database file, so a rebuild deletes only the `zcash_client_sqlite` file.** Rejected for now: it doubles the files an operator backs up and restores together, and existing wallets would need a migration that moves their ledger rows. Building the replacement beside the live file and carrying the ledger across gets the same survival with one file.
- **Rebuild with `rewind_to_chain_state` and a birthday reset instead of a fresh database.** Rejected: it preserves blocks, trees, and transactions below the pruning floor, which is exactly the derived state a rebuild exists to discard after rewinds failed to cure it.
- **Rebuild by truncating to the birthday's chain state.** Rejected for the same reason: `truncate_to_chain_state` keeps notes, nullifier maps, transparent outputs, and subtree roots, so corruption in them would survive the last-resort repair.
- **Wait for a new Zinder depth signal before rewinding deep.** Rejected: `ChainReorged.reverted` already carries the fork point, and Zinder's cursor locator already replays or synthesizes a reorg on resume. No contract change is needed.
